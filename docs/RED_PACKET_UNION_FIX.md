# 企业红包解析与领取规则修复

## 已复现的问题与修改

- 统一消息观察层的 CDATA 正则少匹配一个右方括号，使 `nativeurl` 末尾多出 `]`。例如末尾参数 `sendid=union` 被读成 `sendid=union]`；红包执行器优先使用观察层结果，因此仅修红包工具类仍无法修复主入口。两处现共用 `XmlValueReader`，同时支持多行文本和 XML 实体单次解码。
- 明确的企业红包协议被漏判；非 1005 scene 又会提前结束判定。企业协议、结构化企业字段和企业会话现优先判定，普通 scene 保留。普通祝福语含“企业微信 / wework / wxwork / union_source”不会改变请求类型，`c2cbizmessagehandler` 也不单独作为企业标记。
- UI 启动缺少 `scene_id`，微信按默认 1002 走普通收包。`RedPacketUiAutomator.createReceiveIntent` 统一设置正确场景、`key_way=0`、原始地址、会话与发送者。
- 入口按聊天规则选择领取方式，执行器却再次检查旧版全局方式，导致相反配置直接退出。静默执行器现检查有效规则；UI 执行器使用明确登记的 UI 任务。总开关仍控制入口、异步点击、收包回调和重试。

## 版本依据

已导出并核对 8.0.49、8.0.58、8.0.66、8.0.68、8.0.72、8.0.74、8.0.76、8.0.77、8.0.78、8.0.79 的原生 Union 构造器、回调和 UI 调用。

- 全部版本 Union 收包均为六参数；拆包在 8.0.49/58/66/68 为九参数，8.0.72/74/76/77/78/79 为十参数。现有签名兼容分支保留，回归覆盖两种拆包构造。
- 全部版本直接声明 `onGYNetEnd(int,String,JSONObject)`；第九参数为 `timingIdentifier`，第十参数为可选 `left_button_continue`。
- 原生 UI 读取 `scene_id` 决定普通或企业分支，并读取 `key_way`，默认值分别为 1002 和 0。8.0.49 的企业调用方是 `LuckyMoneyNotHookReceiveUI`；其余九个版本还存在 `LuckyMoneyNewReceiveUI` 调用。
- 本轮补丁没有写死新的混淆类名，也没有更改 DexKit 定位与缓存。

## 验证

```sh
node scripts/run_redpacket_parser_tests.cjs
node scripts/run_redpacket_silent_tests.cjs
node scripts/run_message_parser_tests.cjs
```

回归脚本使用本地 Gradle 缓存中的 Kotlin 编译器与依赖，缺少 `org.json` 时可通过 `JSON_JAR` 指定真实 JAR。测试使用受控的网络、Hook 和界面替身，不发送真实红包请求。

- 红包解析回归覆盖企业协议、scene 优先级、祝福语误判、多行 CDATA 和实体单次解码；新增一万字符纯文本、一万组文本/CDATA 混合片段、长 CDATA 伪标签保护及拒绝嵌套 XML 的完整返回值断言，防止内容重复分支的递归回溯触发 JVM 栈溢出。
- 静默回归覆盖收拆响应归属、九/十参数构造、双向模式冲突、总开关和延迟重试。
- UI 回归覆盖企业页面参数、任务登记、手动页面保护及关闭总开关后的延迟点击。
- 消息解析回归直接编译实际解析器与消息模型；补充观察层地址、企业分流、发送标识、实体和多行文本断言。
- 所有修改的生产 Java/Kotlin 文件已使用真实 Android SDK、Xposed API 和项目已有编译依赖独立编译通过；这不等同于完整 APK 构建。

## 验证边界

用户在安装 6.5.6（606）R8 包并重启手机后确认企业群红包可领取，同时确认此前模块不显示及旧版本显示属于手机侧问题。这是该设备上的用户实测反馈，不代表全部微信版本实机验证。按用户要求，后续移除临时诊断输出和消息计数，仅保留真实错误与异常日志，不改动领取流程。

没有连接用户手机，也没有执行真实领取，不能把这些结果视为十版本实机成功。原生与静默实现的 `inWay`、本人资料来源、空 `timingIdentifier` 门控差异，以及消息 Hook 实际安装和入口去重是否命中用户故障，仍需设备日志确认。本轮未根据这些待验证差异改写支付请求或消息观察调度。
